## Fixture-b correction after preserved runtime-b failure

The original source and runtime-b FAIL remain unchanged. Original stage 41 injected X and called the production button action in the very same ClientTick.Post that first observed the vanilla hotbar mapping changing local selected=1. Minecraft.tick calls gameMode.tick before handleKeybinds; MultiPlayerGameMode.tick sends a changed carried item on the following tick. Therefore the artificial speed action could overtake the ordinary selected-slot packet. The runtime failure confirms server selected=1 by the delayed check, but the earlier speed action was rejected for the previous native-base slot.

Fixture-b adds only an explicit observation barrier between local slot change and opening/clicking X: poll the real server selected slot until it equals 1. It does not call the packet handler, mutate the selected server slot, resend the speed action or reduce the final speed assertion. All original assertions for server selected=1, new staff speed=32 and old base slot without staff component remain identical. The new barrier models waiting for the ordinary carried-item action before interacting with a newly rendered GUI. Production bytecode is unchanged. This source has not been compiled or run by its author.

Boundary: fixture-b does not cover a zero-tick UI interaction race. The original synchronous injected click preceded any user-visible UI frame and did not wait for native selected-slot synchronization; this diagnosis does not prove all potential production races absent.
